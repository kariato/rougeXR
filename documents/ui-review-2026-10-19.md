# Screen and controls review

Reviewed 19 October 2026. Live inspection: welcome, desktop gameplay, spatial game menu, spatial inventory at the available browser window size. Source review: map, camera modes, touch controls, tools, save/load, replay, results, effects/discoveries, and keyboard handling. Headset interaction and physical touch use were not tested.

## Main finding

The interface combines a desktop application toolbar, a spatial game interface, and a persistent HTML action bar. They compete for space, repeat actions, and use different visual treatments. The dungeon should be the dominant screen, with a small status display and one predictable navigation system.

## Priority findings

1. **High: controls extend outside the visible window.** The toolbar is a single nonwrapping row above 760px; its many fixed-width children overflow at the inspected window size, leaving Load, XR, Sound, and Tools offscreen. Spatial panels also appeared clipped at the right edge. Verify both canvas sizing and panel bounds when the available app panel changes size. Sources: `index.html` toolbar and media query; `three-view.ts` resize; `main.ts` ResizeObserver.
2. **High: navigation and actions are duplicated.** Save/load and sound appear in the toolbar and spatial menu; Search/Rest/Pick up/stairs appear in the action bar and spatial menu; Inventory and Discoveries also exist inside Tools. Choose one primary player navigation structure per device. Retain shared behavior between desktop and XR.
3. **High: player features are mixed with diagnostics.** Tools contains inventory/discoveries beside seeds, fixtures, replay, state inspection, cycle traces, and authoritative reveal. Give Inventory and Journal direct player access; move technical controls behind a separate Developer tools entry.
4. **Medium: status and messages consume excessive persistent space.** Large framed spatial panels remain visible, including an empty Messages panel. Use a compact health/depth/status strip, transient messages, and an expandable history. Hide the empty message surface.
5. **Medium: all menu entries compete equally.** Search, save name, volume, Restart, Map/POV, and Close look like peers. Remove routine gameplay actions from the pause menu; group Continue, Save/Load, Settings, Controls, and Restart. Use one clear Close/Back position. Keep destructive actions separated and consistently confirmed.
6. **Medium: context has little influence on controls.** Both stair directions and Pick up remain available regardless of the local feature; disabling currently mostly covers replay and pending decisions. Offer the relevant interaction near the crosshair and explain unavailable actions. Keep Search and Rest reachable without an oversized permanent command strip.
7. **Medium: inventory lacks a clear item/action hierarchy.** List rows, headings, page count, and pagination share the same framed button treatment. Previous/Next appear even on page 1/1. Use distinct heading, list, selected-item details, and action styles; hide unnecessary pagination. Put targeting directions into an explicit targeting step for Throw/Zap.
8. **Medium: camera controls duplicate terminology.** Adjacent selectors both initially say First person, although one chooses renderer and the other chooses camera. Offer a single View control with First person, Orbit, Tabletop, and Map choices.
9. **Medium: keyboard behavior depends on residual focus.** I/M and game bindings ignore focused buttons; after toolbar interaction, shortcuts can appear unresponsive. Pressing I while the menu is open closes it rather than opening inventory. Make navigation transitions explicit and restore game focus predictably. Canvas labels are descriptive strings, not individually focusable menu controls; provide semantic keyboard-accessible desktop equivalents.
10. **Medium: touch layout favors fitting controls over prioritizing them.** A wrapped toolbar and horizontally scrolling command strip coexist with joystick and Attack. Use a compact touch header, thumb-accessible movement/attack, and one contextual interaction. Review landscape and safe areas on real devices.

## Proposed screen organization

| Screen | Primary content and controls | Secondary content |
| --- | --- | --- |
| Welcome | Continue most recent save when available; New adventure | Browse saves; brief controls introduction |
| Gameplay | Dungeon, compact HP/depth, relevant interaction, Inventory, Menu | Expandable messages and status details |
| Inventory | Item list, selected item, relevant actions | Explicit targeting and identification flows |
| Journal | Discoveries and message history | Status effect descriptions |
| Pause menu | Continue, Save, Load, Settings, Controls | Confirmed Restart; Developer tools |
| Settings | View, audio toggle/volume, available XR entry | Device-specific control preferences |
| Results | Outcome, cause, score, Restart/Load | Discoveries and detailed run statistics |
| Developer tools | Fixtures/seed, import/export, replay, inspector, events | Cycle trace and authoritative reveal |

## Visual direction

Use the welcome screen's dark slate and restrained gold as the starting point. Standardize typography, spacing, borders, panel surfaces, button sizes, selected states, and focus states. Give headings and passive information their own treatment instead of rendering them as buttons. Desktop and XR should share labels and organization while using layouts appropriate to each display.

## Recommended implementation order

1. Fix viewport/header overflow and guarantee access to Menu and Inventory across supported sizes.
2. Consolidate player navigation; separate diagnostics; combine view selection.
3. Reduce persistent HUD/message surfaces; introduce contextual interactions.
4. Rework inventory and menu hierarchy; align welcome, settings, and results styling.
5. Verify keyboard focus, touch layouts, and XR behavior.

Acceptance checks: no clipped controls at narrow desktop, phone portrait, or landscape sizes; no horizontal toolbar scrolling; all player features reachable without opening diagnostics; one clear navigation path per feature; correct context actions; fully keyboard-operable player menus; no empty message panel; pagination only when needed. Existing HUD tests check viewport area and page width but do not prove that every control or projected spatial panel is inside the visible viewport.

## Implementation follow-up

The cleanup keeps XR/VR as the primary interface. Spatial panels remain selectable by tracked controller rays, with hover feedback, a shared panel surface, and separate Adventure, Actions, Settings, Controls, Messages, Inventory, and targeting views. The browser shell now keeps immersive entry prominent and places fallback controls behind Desktop options; diagnostics remain explicitly separated.

Status is compact and hidden while a spatial menu is open. Empty message surfaces are removed; recent messages expire and remain available in history. Browser viewport fitting now considers both dimensions, while immersive controls keep their physical scale independently of the mirror window. Single-page pagination is removed and passive labels no longer act as buttons.

Hardware acceptance remains pending; use the spatial UI section of [the XR device checklist](xr-device-checklist.md) to validate readability, controller targeting, mirror resizing, and entry/exit on the target headset.
